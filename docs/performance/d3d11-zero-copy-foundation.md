# D3D11 零拷贝基础层验证

验证日期：2026-07-11

机器：Windows 11、NVIDIA GeForce RTX 4090

素材：仓库基准脚本生成的 3840×2160 H.264 测试视频

## 本阶段结论

底层已经具备共享 D3D11 设备、GPU Frame 持有、CPU/GPU 双存储和按需回读能力。实验路径可以让 FFmpeg 解码后的 D3D11 纹理留在显存中，不再立即下载、转换并复制成 `QImage`。

这仍是底层基础验证，不代表应用预览已经全程零拷贝。实验开关默认关闭，并且当前只允许独立 `FFmpegReader` 使用；时间线、多轨、特效以及 Qt 预览继续走稳定的 CPU/QImage 路径。

## 4K 实测

统一读取前 60 帧，结果如下：

| 路径 | 吞吐 | GPU→CPU 下载 | CPU 图像复制 | 色彩转换 | 返回存储 |
| --- | ---: | ---: | ---: | ---: | --- |
| 现有 D3D11 路径 | 36.99 fps | 76 次 | 76 次 / 945,561,600 字节 | 1163.3 ms | CPU |
| 实验零拷贝路径 | 133.46 fps | 0 次 | 0 次 / 0 字节 | 0 ms | 60/60 GPU |

实验路径在这项“只解码、不显示、不做时间线合成”的微基准中约为现有路径的 3.6 倍。这个倍率不能直接当成最终软件预览或导出加速比例；它只说明被移除的下载、RGBA 转换和内存复制确实是当前底层的重要成本。

对最后一帧主动调用 CPU 像素接口时，存储状态从 GPU-only 变为 GPU+CPU，产生一次 33,177,600 字节回读，耗时约 17.8 ms。回读结果与现有路径的 RGBA SHA-256 完全一致，且整个测试没有固定 D3D11 表面池告警。

## 已落地的边界

- 一个进程内复用同一个 D3D11 设备，并记录显卡名称、序号和 LUID。
- `Frame` 支持 CPU、D3D11、D3D11 已回读三种状态。
- 只有访问 `GetImage()`、`GetPixels()` 等 CPU 接口时才回读，并缓存回读结果。
- GPU Frame 缓存限制在 20 帧预览窗口内，避免耗尽 FFmpeg 固定解码表面池。
- 保留稳定回退：默认开关关闭、旋转素材禁用、挂入 `Clip`/时间线后禁用。
- 暴露解码、下载、复制、转换耗时和字节数，后续可以做应用内性能面板。
